## 1. 自動テスト（xUnit）

`FlowGraphModelBuilderTests` に追加する。フィクスチャは既存の `ApplicationFixtures.Snapshot` と `Build` ヘルパー（`ProductionCalculator.Calculate` → `FlowGraphModelBuilder.Build`）を使う。
交差数の検査は、モデルの公開情報（各ノードの `Rank`・`Order` とエッジ一覧）から仕様どおりの計測を行うテスト側ヘルパー（ランク境界ごとの区間化＋順序位置の逆転対の計数）で行う。計測は本体の内部実装であり公開面は増やさないため、テスト側に同仕様の計測を持たせる（暫定解釈）。

| ID | 対象 | 内容 | 期待 |
|---|---|---|---|
| FG-56 | 下流バリセンター | 採取のみのアイテム（先行ノードなし）が消費設備のある計画を、Id 昇順で消費設備から離れる位置関係になるフィクスチャで組み立てる | 採取アイテムの順序が消費設備の直上流の位置へ寄り、該当エッジの交差が解消される |
| FG-57 | 交差解消 | 報告画面相当の構造（採取アイテム 2 個が消費設備 2 台へ逆向きに供給して Id 昇順では交差する）フィクスチャ | 採用順序の交差数が 0 になる（テスト側計測ヘルパーで計測） |
| FG-58 | 補間区間の計測 | 複数ランクを跨ぐエッジが、中間ランクで順序が入れ替わる他エッジと交差するフィクスチャ | 線形補間した順序位置の逆転が交差として数えられ、最良候補で解消される |
| FG-59 | 目標加重と第 2 キー | 交差数が最小の順序候補に、目標アイテムとその設備が近接するものとしないものが混在するフィクスチャ | 加重で生成される目標隣接の候補が採用され、設備ノードと目標アイテムノードの順序番号差が最小側（同一カラムまたは隣接カラム）になる。加重や第 2 キーがなければ交差数が並ぶ非隣接候補に負けうる構成とする |
| FG-60 | BM 隣接維持 | 環境供給設備（散布機）を持つ計画で下流掃引を含む掃引を行う | 散布機が最小層の利用設備の直後に置かれる規則が全表示で維持される |
| FG-61 | 決定性 | 同一入力で `Build` を 2 回実行する | `Rank`・`Order` が完全一致する |
| FG-62 | 最良候補 | 掃引が交差を増やさないことを、交差が残るフィクスチャで確認する | 採用順序の交差数が初期の Id 昇順順序の交差数を上回らない。候補に従来方式（上流のみ 4 パス）の結果が含まれるため、従来の出力を上回らないことも構造上保証される |

既存テスト全緑（`dotnet test`）を回帰として確認する。FG-01〜55 の順序アサーションは新順序規則で結果が変わりうるため、変わった場合は新規則の期待値へ更新した旨を PR 本文に記録する。

## 2. 手動確認項目（ブラウザプレビュー）

WebGPU 対応 Chrome で公開アプリの計算ページを開く。
主な検証計画は報告画面相当の計画（重息壌ガスを目標に含む環境利用計画）と、ノード・エッジが多めの計画を使う。

| ID | 確認内容 | 手順 | 期待 |
|---|---|---|---|
| MN-178 | 報告画面相当の交差解消 | 重息壌ガスを目標に計算し、グラフを縦表示で見る | 不活性ガス・息壌ガスのような採取アイテムが消費設備方向へ寄り、報告時の交差が減る |
| MN-179 | 目標設備の近接 | 複数の生産経路を持つ目標の計画を出す | 目標アイテムとその生産設備が近接して配置される |
| MN-180 | 大きめ計画の回帰 | ノード・エッジが多い計画を出して交差の見た目を確認する | 極端な交差の増加や壊れた配置がない |
| MN-181 | 表示切替の同一性 | 縦横切替・集約/台数分切替・最大化を行う | 全表示で同じ順序（同一モデル）が使われ、切替で崩れない |

## 3. 受け入れ条件との対応

- FG-56・FG-57・MN-178 が採取アイテムの消費設備への接近と交差解消を、FG-58 が補間区間の計測仕様をカバーする
- FG-59・MN-179 が目標加重の効果をカバーする
- FG-60 が BM 隣接規則の維持を、FG-61 が決定性を、FG-62 が最良候補採用（退化しないこと）をカバーする
- MN-180・MN-181 が実画面での回帰をカバーする
- `dotnet build`・`dotnet test` 全緑と `tools/validate_master.py` 通過を併せて確認する
