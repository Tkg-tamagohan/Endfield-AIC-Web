## 1. スコープ

### 背景と問題

「不活性ガスと息壌ガスの位置を入れ替えたほうが、ノード間の交差が少なくなり、見やすくなる」という報告を起点に、フローグラフのランク内順序（`FlowGraphModelBuilder.AssignRanks` の順序付け部）を調査した。

現行の順序付けは、先行（上流）ノード位置のバリセンター平均で 4 パス並べ替えるだけで、後続（消費側）ノードの位置を一切見ていない。
そのため、不活性ガス・息壌ガス・水のような採取のみのアイテムノードは先行ノードを持たず、バリセンターが自分自身の現在位置に退縮して初期の Id 昇順から全く動かない。
結果として消費設備から遠い位置に残り、消費方向へ引く供給エッジ同士の交差を生む（報告画面の不活性ガス→ガス散布機と息壌ガス→赤銅圧力タンクの交差がこの構造である）。

層割り（BF〜BH・BM の層規則）自体は健全なため、変更はランク内順序だけに限定する。
仕様決定 CR で「双方向バリセンター掃引＋交差数計測による最良順序採用＋目標出力エッジの支配的重み」が確定した。

### やること

- `AssignRanks` のランク内順序を、上流側（先行ノード位置）と下流側（後続ノード位置）のバリセンター掃引を交互に行う双方向の並べ替えへ改める
- 掃引で確定した各順序候補の交差数を計測し、最小の順序候補を採用する交差数計測を追加する
- バリセンターを加重平均にし、目標アイテムへの出力エッジに支配的重みを付ける
- 掃引の終了条件を収束判定＋上限パス数へ置き換える
- xUnit FG-56〜 と手動確認 MN-178〜 を実施する

### やらないこと

- 層割り（BF〜BH・BM の層規則・`AssignRanks` の層決定部）は変更しない
- ダミーノード挿入による本格的な Sugiyama レイアウトや、隣接交換（sifting）による微調整段は入れない。本 Phase の方式で残る交差が問題になる場合に後続 Phase で検討する
- 表示方向（縦・横）や集約・台数分による順序の分岐はしない（BJ と同じく共通モデルの方針）
- `flow-graph.js`・`FlowGraph` コンポーネントなど JS・描画側は変更しない。JS は `rank`・`order` を座標へ写像するだけで順序の決定に関与しないため、モデルの Order 値の変更のみで済む
- 交差数計測の結果をモデルやログへ出力しない（内部の選択指標としてのみ使う）

## 3. 設計の詳細

### 3-1. 双方向バリセンター掃引

現行は `for (int pass = 0; pass < 4; pass++)` で「全ノードのバリセンター（先行位置の平均）を計算 → 各ランクをソート → BM の隣接挿入」を繰り返す構造である。
これを、掃引方向を交互に変える双方向掃引へ改める。

- 上流パス: ノードのキーは先行ノード位置の加重平均。先行集合は従来どおり `preds`＋`virtualPreds`（BM の仮想先行）
- 下流パス: ノードのキーは後続ノード位置の加重平均。後続は描画される全エッジの宛先を使い、環境消費など終端ノード宛のエッジ（`succs` に含まれる終端宛）も含める。層割りで除外した終端宛エッジも描画対象なので、順序付けには含める
- 位置のキーは従来どおり `rank * 1_000_000 + order` の大域位置を両方向で共用する
- その方向に隣接ノードを持たないノードは現在位置を維持する（従来の退縮規則を両方向に適用）
- 最初のパスは上流側とする（従来のパスと同じ向きで始めて挙動の連続性を保つ）
- 各パスでソート後に BM の隣接挿入（環境供給設備を最小層利用設備の直後へ移す規則）を従来どおり適用し、`order` を更新する
- 初期順序はランク内の Id 昇順（不変）

加重平均の重みは §3-3 のエッジ重みを使う。`virtualPreds` 由来の仮想先行は重み 1 とする（隣接の強制は挿入規則が担うため、キーへの寄与は弱くてよい）。

### 3-2. 交差数の計測と最良候補の採用

各パスで順序が確定するごとに、その順序全体の交差数を計測し、最小の順序候補を保持して最後に採用する。

- ランクは 0..maxRank（rank = maxLayer - layer）。rank k と k+1 の境界を跨ぐエッジを、その境界における区間として扱う
- 境界 k|k+1 を跨ぐエッジ e のランク k 側の順序位置は、端点ノードがランク k にあればその `order`、なければ両端点の (rank, order) の線形補間とする。rank k+1 側も同様に求める
- 同一境界を跨ぐ 2 区間について、両端の順序位置の差の符号が厳密に逆転する（積が負）とき交差 1 件と数える
- 端点を共有するエッジ対は交差として数えない。各エッジの順序位置はランクについての一次関数であり、共有端点ではその差が 0 になるため、共有端点ランクより外側の全境界で差の符号は一定であり、厳密な逆転はどの境界でも起き得ない（複数ランクを跨ぐ長いエッジ同士でも同じ）
- 全ランク境界で合計したものをその順序候補の交差数とする
- 同一ランク内の両端を持つエッジ（環境供給設備への消費エッジなど）は境界を跨がないため計測対象外である

本規模（ノード数十個・エッジ数十本）では、境界ごとの区間対を総当たりで比較する素朴な実装で十分である（暫定解釈。逆転数の高速計数は不要と判断した）。
計測は内部実装に留め、公開面は増やさない。テストでは `FlowGraphModel` の公開情報（各ノードの `Rank`・`Order` とエッジ一覧）から同仕様の計測ヘルパーをテスト側に書いて検査する（暫定解釈。`InternalsVisibleTo` を新設しない方針）。

### 3-3. 目標出力エッジの支配的重み

ユーザー決定 E「最終目標アイテムとそのための設備は近いほうが望ましい」に従い、目標アイテムへの出力エッジに支配的重みを付ける。

- 対象エッジ: `Kind == RecipeOutput` で宛先アイテムノードの `IsTarget` が真のエッジ
- 重み: そのエッジの両端点それぞれに接続する描画エッジ数（そのエッジ自身を含む）の大きい方の値。両端点の加重平均において、他の全隣接エッジ（重み 1・各端点でエッジ数−1 本）の合計を必ず上回る最小の整数になる
- 他のエッジは重み 1 とする

採取のみのアイテム→消費設備の供給エッジは重み 1 のままである。重み付けの効果は「目標とその設備をまず近接させ、残りの隣接関係はその拘束を受け入れて残りを詰める」順序になることである。

### 3-4. 終了条件と最良候補の採用

- 上流・下流の掃引を交互に行い、直近の一往復（2 パス）で全ランクの順序が不変になった時点で打ち切る
- 上限パス数は実装定数（12 を目安、暫定解釈）とする
- 各パス後に交差数を計測し、最小の順序候補を `nodesByRank` の複製として保持する。終了後に最良候補を採用して `order` を確定する
- 順序候補には従来方式の結果（上流側のみのバリセンター掃引と BM 隣接挿入を従来の固定 4 パスで行った順序）も含める。双方向掃引とは別に従来方式を一度だけ評価して候補へ加えるだけでよい
- 交差数が最小の候補が複数あるときは、目標アイテムへの出力エッジ（§3-3 の加重対象）について両端ノードの順序番号差の絶対値の合計が最小の候補を採用し、同量なら先に現れた候補とする。これにより加重で生成された目標隣接の候補は、交差数が並ぶ限り必ず採用される

従来方式の順序が候補に含まれるため、採用順序の交差数が従来を上回らないことが構造上保証される。第 2 キーの順序番号差は加重対象エッジだけを見るため、他の隣接関係を損なわない範囲で目標と設備の近接が優先される。

### 3-5. 確定的動作

- バリセンターはソート前の `order` に対して一括で計算し、同率は `StringComparer.Ordinal` の Id 比較（従来どおり）
- `Dictionary` の列挙順には依存しない（ランクごとの `List<string>` で順序を管理する従来構造を維持）
- 掃引回数・候補選択とも入力が同じなら結果は一意である

## 4. 受け入れ条件

- 採取のみのアイテムが消費設備方向へ寄り、報告画面相当の計画（目標に重息壌ガスを含む環境利用計画）で供給エッジの交差が減る
- どんな計画でも採用順序の交差数が候補群の最小であり、従来（先行のみ固定 4 パス）より交差が増えない
- 散布機が利用設備の隣に置かれる BM の規則・同率 Id 昇順・全表示での共通モデルが維持される
- 目標アイテムとその生産設備が近接して配置される

## 6. リスクと引き継ぎ

- 交差数の計測はランク境界の順序位置ベースの近似であり、描画されるベジェ曲線の幾何学的な交差と厳密には一致しない。曲線の途中での接触や制御点の張り出しによる見かけの交差は計測対象外（暫定解釈として残す）
- 後退エッジの側面張り出し量（CO）は順序に依存するため、順序変更で張り出し量が変わりうる。CO の規則自体は不変
- 加重により目標設備の近接が他の隣接関係を押しのけて、別の交差を増やす配置が候補として現れうる。最良候補採用があるため最終的な交差数は増えないが、「加重が効いたのに交差が増えた」組合せの起き方は実装時の実測で確認する
- 採番は並行セッションと衝突しうる。push 前に main の `decision-records.md`・テスト仕様書の最新番号を再確認する
