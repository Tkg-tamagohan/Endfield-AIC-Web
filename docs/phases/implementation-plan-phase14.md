# Phase 14 実装詳細計画

**対象フェーズ**: Phase 14（管理ツールのアイテム選択簡易化）
**前提ドキュメント**: [implementation-plan.md](../implementation-plan.md)、[requirements.md](../requirements.md)、[decision-records.md](../decision-records.md)
**関連ドキュメント**: [test-specification-phase14.md](test-specification-phase14.md)（本 Phase のテスト仕様）

> 本書は Phase 14 のチェックリストを、作業者が追加の判断なしに実行できる粒度へ分解したものである。
> 成果物は原則として 1 つの PR にまとめて main へマージする。
> マスタ構成（モデル、スキーマ、JSON）は変更しない。UI の入力補助のみを対象とする。

## 1. スコープ

### やること

管理ツールのアイテム関連の入力を簡易化する。

- アイテム編集のカテゴリ欄で、文書内の既存カテゴリを補完候補から選べるようにする。自由入力は維持する
- レシピ編集のアイテム選択（入力、出力、固定消費の各行）で、選択肢をカテゴリで絞り込めるようにする

### やらないこと

- マスタ構成の変更。`Item.Category` は引き続き自由文字列とし、`data/master.json`、スキーマ、`MasterValidator` の必須違反は変えない
- 公開版 App、Domain、Infrastructure の変更
- マップ編集、環境編集、計算プレビューのアイテム選択。マップ編集は天然資源で絞り込み済みであり、その他 2 箇所は今回の依頼対象外とする
- `RefSelect` の仕組み変更（検索コンボ化など）。既存のネイティブ select を維持する

## 2. 現状

- `ItemsPage.razor` のカテゴリ欄は自由入力の `<input>` であり、既存値を知るには一覧の検索（カテゴリを検索対象に含む）か文書の確認が要る
- `RecipesPage.razor` の `_itemOptions` は全アイテムで構成され、入力、出力、固定消費の 3 箇所で共有されている。アイテム数が増えると目的の項目を選びにくい
- `RefSelect` は値と表示名のペア（`SelectOption`）のリストを受け取るネイティブ select で、選択肢の絞り込みやグループ化の仕組みを持たない

## 3. カテゴリ欄の補完（アイテム編集）

- カテゴリの `<input>` に `list="item-category-list"` を付け、同ページ内に `<datalist id="item-category-list">` を置く。候補は §5 のカテゴリ列挙結果
- datalist は入力に候補を添えるだけで自由入力を妨げないため、既存の入力操作と新規カテゴリの打ち込みはそのまま残る
- 入力欄の下にヒントを一行添える（「既存のカテゴリが候補に出ます。新しい名前も入力できます。」の意）

## 4. カテゴリ絞り込み（レシピ編集）

- レシピ編集パネルの上部（「所属イベント」の下）に「アイテム絞り込み」の select を 1 つ置く。候補は先頭の「すべてのカテゴリ」に §5 のカテゴリ列挙を続けたもので、初期値は「すべてのカテゴリ」
- 絞り込み中は、入力、出力、固定消費の 3 箇所すべてでカテゴリ一致のアイテムだけを出す
- 行の現在値が絞り込み条件に合わないとき、そのアイテムを選択肢の末尾に残す。ネイティブ select は値が選択肢にないと先頭候補を表示してしまうため、この措置がないと未変更の行が別アイテムに化けて見える
- 絞り込み状態はページの UI 状態（`_itemCategoryFilter`）として保持し、レシピの切替で初期値に戻さない

## 5. 実装構成

絞り込みと候補列挙の判定は Application の純粋関数に置き、razor は結果を `RefSelect` の `Options` に渡すだけにする（remaining-issues.md が挙げる UI 状態遷移のテスト空白を増やさない方針）。

- Application に `ItemCatalog`（静的クラス）を追加する
  - `Categories(items)`: `Category` が空でない値を、文書内での初出順に重複除去して返す
  - `FilterByCategory(items, category)`: category が null または空なら全件を、指定があればカテゴリ一致のアイテムだけを返す
  - `OptionsForSelection(items, category, currentItemId)`: 絞り込み結果に現在値のアイテムが無ければ末尾へ追加して返す（§4 の表示ずれ防止）
- `ItemsPage` は `Categories` の結果を datalist の候補に流す
- `RecipesPage` は `OptionsForSelection` の結果を `SelectOption` に写して各行へ渡す
- 行の追加（`AddInput`、`AddOutput`、`ToggleFixedConsumption`）で既定値に使う先頭アイテムは、絞り込み後の一覧の先頭に追従させる

## 6. 確定した UI 上の判断

計画策定時に確認した UI 上の判断（2026-10-01 確定）。実装中に変更する場合は本節を更新する。

1. カテゴリ欄は `<input>` と `<datalist>` の組み合わせによる補完とする。既存値の select を入力欄の横に置く案は、部品が 2 つになるため見送った
2. 絞り込みの select はレシピ編集パネルに 1 つとし、3 箇所へ共通に適用する。表ごとの独立絞り込みは部品数が増えるため見送った
3. カテゴリ候補の並びは文書内の初出順とする。五十音ソートは master の並びと対応が付かず、頻出順に並べる根拠も現時点では薄い
4. 絞り込み中の既存値は選択肢の末尾に残す（§4 のとおり）
5. `Category` が空のアイテムは絞り込み候補に出さず、「すべてのカテゴリ」選択時のみ選択肢に出す。`Category` 空は検証違反であり、新規作成直後の一時状態のみを想定する

## 7. テスト

[test-specification-phase14.md](test-specification-phase14.md) に従う。
`ItemCatalog` の純粋関数は xUnit で採番してカバーし、razor の UI 状態遷移は残課題のとおり対象外とする。
ブラウザプレビューによるユーザー確認は実装後に別途挟む。

## 8. 受け入れ条件

- カテゴリ欄のフォーカスや入力に応じて既存カテゴリが候補に出て、候補にない新しい文字列もそのまま確定できる
- レシピ編集でカテゴリを選ぶと、入力、出力、固定消費のアイテム選択肢がそのカテゴリのアイテムだけになる
- 絞り込み中でも、条件に合わない既存値の行が別アイテム表示に化けない
- `dotnet build` と `dotnet test` が全緑である
