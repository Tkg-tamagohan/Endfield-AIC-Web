## 1. スコープ

### やること

- レシピの `Outputs` を 0 件許容とし、出力なしレシピ＝「処理レシピ」（入力を消費して産出しないレシピ）を登録可能にする（仕様決定 BZ）。スキーマの `minItems` 緩和・検証の撤去・管理ツールの対応を行う
- 通常の需要展開が収束した後、最終余剰に対して処理ランを投入する計算パスを追加する（仕様決定 CA）
- 処理対象アイテムごとの処理レシピ・ペアの既定選択を実装する（仕様決定 CB）
- 処理ランを設備台数・消費電力・固定消費・環境要件へ通常ランと同じ規則で計上し、処理消費を需要として扱う（仕様決定 CC）
- 素材行で処理による消費を識別できる表示にする（仕様決定 CC）
- フローグラフで処理設備のノードを持たず、処理消費のあるアイテムノードを紫色で描いてメタ行に処理情報を併記する（仕様決定 CD）
- 管理ツールの Id・名前自動提案（仕様決定 BU）を出力なしレシピへ適用しない（仕様決定 CE）

### やらないこと

- 処理レシピのペア代替選択 UI。ペア選択 UI は需要アイテム起点の枠組みであり、処理レシピはそこに載らないため対象外とし、残課題として記録する（§8）
- 処理レシピを実データへ登録する作業。廃水処理機のレート等はゲーム実データであり、管理ツール経由でユーザーが行う
- 計算目標アイテムの余剰処理（CA で対象外）
- 採取（外部調達）供給分の処理。余剰判定は「生産−需要」とし、採取分は対象にしない（§7 暫定解釈 1）
- 処理専用の警告種別の追加。適格な処理レシピ・ペアがない場合は従来どおり余剰として残す（CC）
- 層割りモデル（BF〜BH・BM）の変更。CD はノードの有無と配色・メタの変更であり、層割りには触れない

## 2. 用語

- **処理レシピ**: `Outputs` が 0 件のレシピ。入力アイテムを消費して何も産出しない（仕様決定 BZ）。廃水処理機（汚水・壌晶廃液・不活性壌晶廃液を無にする設備）のような廃棄処理設備を表現する
- **廃水系アイテム**: 処理レシピの入力に登場するアイテム。最終余剰が処理ランで消費される（仕様決定 CA）
- **処理ラン**: 処理レシピの稼働ラン。余剰量分だけ登録される `RecipeRun` で、設備台数・消費電力等の集計は通常ランと同じ規則に従う

## 4. 変更詳細

### 4-1. 出力なしレシピの許容（BZ）

- `data/master.schema.json` のレシピ `Outputs` を `minItems: 0` へ緩和する。`Inputs` は従来どおり 1 件以上を要求する
- `MasterValidator` の「Outputs は 1 件以上必要です」の違反を撤去する。`Inputs` 側の必須検査は据置とし、0 件出力のレシピは SortOrder の検査を素通しとする
- 管理ツールの出力行は現行でも 0 行まで削除できるため、UI 変更は出力欄ヒント（「SortOrder 最小の行が主産物」）への「出力 0 件は処理レシピ」の追記に留める
- 出力なしレシピはアイコンの既定解決（主産物由来の `IconKeyFallback`）ができないため、設定しない限りプレースホルダ表示となる。`IconKey` は手動で設定可能
- 出力なしレシピは生産の選択候補に現れない（需要展開は産出レシピを引く経路のみ）。そのため BZ の導入自体は既存計算の結果を変えない

### 4-2. 処理ランの投入（CA）

- `CalculationSession.Run` の収束反復に、環境消費・固定消費の追加需要と同型の「処理需要」の再評価を組み込む。各反復の均衡化（`BalanceToFixpoint`）の後・台数確定と追加需要の計算の前に行い、処理ラン由来の機械数・固定消費・環境消費を同じ反復の追加需要計算に載せる
- 現在余剰は `Produced − (Demand − DisposalApplied)` で評価する。すでに計上済みの処理需要を除いた帳簿で見ることで、処理ラン自身の消費で余剰が消えたように見えて付け外しが振動するのを防ぐ（暫定解釈 7）。処理需要の変更は収束判定（追加需要の変化）に含める
- 処理レシピの入力に登場するアイテムを処理対象とする。評価順はアイテム Id 昇順で決定的とする（暫定解釈 3）
- 計算目標に指定されたアイテムは余剰があっても処理対象外とする
- 処理需要は `ExtraApplied` と同型の差分適用で帳簿へ反映し、反復ごとに現在余剰へ追随して更新する。縮小した生産で需要が余剰を上回った場合も次の再評価で減額されるため、最終的に処理需要が余剰を超えず、処理対象アイテムの新規生産を誘発しない（CA）
- 処理需要の追加で新たに生じる余剰（処理ランの固定消費や環境消費が誘発した生産の副産物など）も、以降の反復で同じ規則の処理対象になる
- 処理のためだけにアイテムを生産しない。適格な処理レシピ・ペアがない場合は需要を加えず、余剰は従来どおり余剰一覧へ残る（警告も出さない、CC）

### 4-3. 処理レシピ・ペアの既定選択（CB）

- 処理対象アイテムを入力に持つ処理レシピ（`Outputs` が 0 件）から、コンテキスト適格なもの（レシピのイベントが有効、ペアの環境が有効）を 1 件選ぶ。選択は `PairSelector` とは別の系として実装し、`Selection`（アイテム→選択ペア）には登録しない（処理ランはそのアイテムの産出レシピではないため）
- レシピの順位: `VersionAdded` 最新 → 対象アイテムの実効処理レート（1 サイクルの対象入力量 ÷ 適格ペアの最小 `CycleTime` ×60 個/分）最大 → `Id` 昇順
- ペアの順位: `CycleTime` 最小、同率は BT の順（`FixedConsumption` なし → `RatePerMinute` 小 → `EnvironmentId=null` → `FacilityId` 昇順）
- 入力に複数アイテムを持つ処理レシピは、評価順最初の対象アイテムの余剰でサイクル数を決め、他入力はそのサイクルに従う消費として需要へ計上する。他入力に余剰が足りない分は通常の需要として残す
- ランのサイクル数は、処理対象の入力すべてについて「残り余剰 ÷ 1 サイクル入力量」の最小値を上限とする。上限に数えるのは残り余剰がある入力と、すでに処理ランが登録された入力（余剰が尽きても対象のままとする）のみで、残り余剰がなく処理対象にもなっていない入力は補助入力として通常の需要に計上し、その分の生産を許容する（暫定解釈 9）。同一の処理レシピが複数の対象アイテムで選ばれた場合は別ランを増やさず 1 つのランにまとめ、後から評価されたアイテムの分は既存ランのサイクル数へ合流させる（合流後も処理対象の入力の残り余剰を超えない）。これにより、2 つ目の対象アイテムが同じレシピを選んだとき先に処理したアイテムの余剰を超えて消費することがなく、補助入力の不足で処理そのものが止まることもない
- 同一アイテムの処理を複数レシピへ分割しない（1 アイテム 1 処理レシピ。R の需要分割禁止と同じ考え方。暫定解釈 2）

### 4-4. 計算結果への反映（CC）

- 処理ランは `RunCycles`・`RunOrder` に登録し、`RecipeRun` として出力する。選択したペア行をランと一緒に保持し（`RecipeRun` へのペア保持か処理ラン専用の構造かは実装時に確定）、`FacilityUnitLayout`・`ResultViewBuilder`・`FlowGraphModelBuilder` のペア解決がそのペアを使うようにする。保持しないと同一設備に複数ペアがあるレシピで先頭ペアへ解決され、CycleTime・環境がずれる
- 機械数（実数・切上げ台数）・消費電力・固定消費・環境の利用機械数は既存の集計がそのまま拾う
- 処理による消費は対象アイテムの需要へ計上する。そのアイテムは素材行に現れ、余剰一覧からは消える
- `Retract` は出力なしレシピのランを対象外とする。`Selection` に現れないランは現行の評価では required=0 と扱われて除去されるため、除去対象から明示的に除外する
- 処理ランのペアが環境を要する場合、その機械数は環境の利用機械数（BQ・BR）に計上する。散布機台数上書きによるカバー上限を超える分は稼働を削り、削られた分は処理需要を減額して整合させ、処理しきれなかった分は余剰として残す（未充足にはしない、暫定解釈 5）
- `BuildFlowAdjustments` は出力なしレシピのランを対象外とする。処理入力への推奨流量制限は意味を持たない
- 未調整ビューでは処理ランもラン倍率でスケールする。処理消費も同じ倍率でスケールして表示し（計画の需要をそのまま見せると全速稼働の処理量とずれる）、未調整の利用可能量を超える分はクランプする。未調整の余剰は処理後の残量を `RecomputeSurpluses` と整合する形で表示する（暫定解釈 8）

### 4-5. グラフ表現（CD）

- `FlowGraphModelBuilder` で、出力なしレシピのランはエッジ生成・容量集計の対象外とする。そのランのみを占有する設備は設備ノードを作らず、処理設備が生産ランや散布機を兼ねる場合は設備ノードを残して通常どおり層割りする
- 台数分表示（`expandFacilities`）のユニット割当は、出力なしランを `FacilityUnitLayout.Allocate` の入力から除いて計算する。処理分のスロットを実体化しないため、処理専用のユニットノードも処理に占有されたユニットノードも出ない（兼用設備は生産・散布機分のユニットのみ出る）
- 処理消費のあるアイテムノードへ、処理量と処理設備の情報（設備名・台数）を保持するフィールドを追加し、BO の緑化と同型に新クラス `fnode-disposal`（紫）で描く。生産消費と処理消費が併存するアイテムも紫とする
- メタ行は「処理 〈設備名〉×〈台数〉・〈処理量〉」系を併記する。文言と台数の取り方（計画の設備要件の切上げ台数とする、暫定解釈 4）は実装時に確定し、ブラウザプレビューで確認する
- 容量超過の赤化は仕様決定 BV で撤去済み（Phase 30）のため、処理表現に容量判定は持たない

### 4-6. 素材行の処理表示（CC）

- 素材行で処理による消費を識別できる表示にする。`MaterialViewRow` への処理量フィールド追加、または供給内訳の消費側注記のいずれかで実装し、表現は実装時に確定してブラウザプレビューで確認する
- 表示側は「出力を持たないレシピのラン」から処理消費を導出する。計画モデル（`ProductionPlan`）への新フィールドは持たせない方針とし、処理ランは通常の `RecipeRun` として識別する

### 4-7. Admin の Id・名前（CE）

- BU の自動提案は出力なしレシピへ適用しない。`RecipeAutoFill` は出力が 0 件の間は提案を計算せず、Id・名前は現在値を維持する（RCP-06 の規則をそのまま拡張する形で確認する）
- 出力行が 0 のレシピの Id・名前は手入力とする。出力を追加して主産物ができれば提案の対象に戻る

## 5. 影響の確認

- BZ は登録の解禁であり、処理レシピが登録されるまでは計算結果に影響しない。同梱マスタ（`data/master.json`）に処理レシピは含まれないため、`tools/validate_master.py` と `BundledMasterDataTests` は回帰確認として通ればよい
- 処理ランは `RecipeRun`・`FacilityRequirement`・`EnvironmentRequirement`・`TotalPowerConsumption` に通常ランと同じ形で現れるため、設備一覧・電力・環境の各表示は既存のまま反映される
- 廃水系アイテムを再利用するレシピがある構成（ゲーム上の実在ケース）は、再利用分が通常の需要として先に充当され、残りの余剰のみが処理対象になる（CA）
- `MasterDataSnapshot` への入力索引追加は新設のため、既存の出力索引の使用箇所には影響しない

## 7. 暫定解釈

実装中に変更する場合は本節を更新する。

1. 余剰の判定は計画の余剰と同じ「生産−需要」とし、採取（外部調達）供給分は処理対象に含めない
2. 同一アイテムの処理を複数レシピへ分割しない（1 アイテム 1 処理レシピ）
3. 処理需要の再評価順はアイテム Id 昇順で決定的とする
4. 処理設備が兼用（生産ラン・散布機兼任）のときメタ行の台数は計画の設備要件の切上げ台数とし、処理分だけの按分はしない
5. 環境を要するペアの処理ランはカバー不足で削られうるが、削られた分は未充足ではなく処理されない余剰として残す
6. 処理需要の帳簿は収束反復の中で増減を再評価する。一時的に需要が余剰を上回っても次の再評価で減額され、最終状態で余剰を超えない
7. 余剰の再評価は処理で計上済みの需要を除いた帳簿で行い冪等とする（処理ランの登録と除去が反復間で振動しない）
8. 未調整ビューの処理消費はラン倍率でスケールした量を未調整の利用可能量内にクランプして表示する
9. サイクル上限に数える「処理対象の入力」は、残り余剰がある入力と処理ランが登録済みの入力とする。残り余剰がなく処理対象にもなっていない入力は補助入力として通常の需要に計上し、その分の生産を許容する。処理対象のアイテムは余剰が尽きても上限の対象であり続けるため、処理のために新規生産されない

## 8. 残課題

- 処理レシピのペア代替選択 UI。需要アイテム起点の枠組みに載らないため本 Phase では持たず、remaining-issues.md へ記録する
- 処理レシピの Id・名前の命名規則が固まれば、BU のフォールバック提案を検討する余地がある（CE）

## 9. 受け入れ条件
