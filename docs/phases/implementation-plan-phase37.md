## 1. スコープ

### 背景と問題

縦表示の後退エッジ（下位層へ戻る辺）は、ソースノード上辺 → ターゲットノード下辺の単一 3 次ベジェで描き、制御点を左右いずれかの側面へ張り出してループを作る（Phase 24、仕様決定 BJ の描画規則）。
張り出し量は `offFor(side)` が「縦スパン間にある全ノード矩形＋余白 10px を曲線が全て避ける最小値」を反復探索で決める（初期値から ×1.6+24 で最大 10 回増分）。

この方式には 2 つの破綻があり、`recipe-heavyXiragen01` の計画で実害として発生した。

1. **回避不能な配置で探索が発散する**。`芽針 → 採種機`（rank4 最左端 → rank1 最右端）は、右側は立ち上がりの掃引がソース行の隣接カード群を必ずまたぎ、左側は復帰の掃引がターゲット行のカード群を必ずまたぐ。どちら側にも「全て避ける」張り出し量が幾何学的に存在しないのに、未収束でも反復は最後の増分値（約 16,000px）を無条件に返すため、実到達約 12,500px の巨大ループを生成する
2. **収束しても巨大になる**。共有設備ノードは最も浅い出力の層に置かれるため（仕様決定 BH の層割りどおり）、`精錬炉 → 炭塊/赤銅塊` が全行をまたぐ後退エッジとなり、採用側の収束値でも張り出し 560〜920px・曲線実到達 1,000〜1,300px の大弧になる（非採用側の候補値は約 2,600px に達した）

結果として世界矩形がノード矩形を大きく超過してフィット計算がノード矩形のみの退避モードに落ち（下限ズームの制約）、弧の大半が画面外へ出る。
また仕様上の空白として、「間のノードカードをまたがないループ」（Phase 24 テスト仕様 MN-98）を**どちら側でも満たせない配置**は定義されていなかった。

### やること

- `edgeGeometry` の縦表示後退エッジについて、張り出し量の反復探索（`offFor`）を廃止し、決定論的な計算へ置き換える（仕様決定 CO）
- 張り出し側は左右それぞれの必要張り出し量を求めて小さい側を採用し、同量のときはソースノードに近い外縁側を選ぶ
- 間のノードカードとの交差を「ノード背面への通過」として許容する旨を仕様へ反映する（エッジは canvas 層、ノードカードはその上の DOM 層のため、交差部分は背面に隠れて見える）
- 手動確認項目 MN-158〜 を実施する

### やらないこと

- 横表示の後退エッジは変更しない。横表示には元々回避機構がなく、制御点張り出しのみの従来描画を維持する
- 前進エッジ（p0 が p3 より上）の接続規則・制御点は変更しない
- 層割り・順序・ノード配置（`FlowGraphModelBuilder`・`update()` のレイアウト部）は変更しない。共有設備が浅い層に置かれるのは仕様決定 BH の挙動であり本 Phase の対象外とする
- 複合経路（折れ線・複数ベジェによる厳密な全カード回避）への拡張はしない。WGSL の帯描画・粒子追従が単一ベジェ前提のためコストが大きく、背面通過で実用上の破綻は解消できると判断した
- Domain・Application・テストコード（xUnit）の変更は行わない

## 3. 設計の詳細

### 3-1. 張り出し量の決定論的計算（仕様決定 CO）

対象は従来どおり `p3[1] > p0[1]` の縦後退エッジのみ。
制御点の張り出し量 `off` を、側ごとに次で求める。

1. `mids`：従来と同じ集合（端点 a・b を除き、`r.y + r.h > loY + 4 && r.y < hiY - 4` を満たすノード矩形。つまり矩形の縦範囲がエッジの縦スパンに交差するもの）
2. 側 s の目標外縁 `E_s`：`mids` のその側の最外縁 ± 余白 `PAD=10`。右なら `max(r.x+r.w)+10`、左なら `min(r.x)-10`。`mids` が空なら `off_s` は下限値のみで確定し、外縁計算は行わない
3. 基準端点 x：右は `max(p0x, p3x)`、左は `min(p0x, p3x)`
4. `off_s = max(下限, |E_s − 基準x| / K)`。`K=0.75` は両制御点を同量ずらしたときの曲線の水平極値に対する近似係数（従来コメントの実測値）
5. 補正：`cubicBounds` で実曲線の極値を評価し、目標外縁へ未達なら不足分 ÷ K を `off_s` へ加算する補正を最大 2 回行う（係数が近似のため、回数固定の補正で収める。反復は「確定した計算の検証」であり探索ではない）
6. 下限は従来の探索初期値と同じ `Math.max(a.w, b.w) / 2 + 32` とし、mids 外縁が近い場合でもループ形状を保つ

側の選択：左右の `off_s` を比較して小さい側を採用する。
両側が同量（差が 1px 未満）のときは、ソース上辺点 `p0` に近い外縁側（`|p0x − E_L|` と `|E_R − p0x|` の小さい側）を選ぶ。
`芽針 → 採種機` は左右とも `off≈112` の同量となり、ソースが左端にあるため左側の小ループになる。

### 3-2. 交差の許容と描画順（仕様決定 CO）

新しい張り出し量は「曲線の水平極値がその側の外縁＋余白へ到達する」ことを保証するだけで、曲線とノードカードの非交差は保証しない。
端点付近でソース・ターゲット行のカードや途中行のカードを曲線がまたぐ場合があり、これは仕様上許容する。

交差が見た目を破綻させない根拠は描画順にある。
エッジは `.flow-canvas`（canvas 層）に描かれ、ノードカードは後続の `.fnode-layer`（DOM 層）にあるため、交差部分は常にカードの背面に隠れて描かれる。
曲線はカードの両側から出入りする弧として見え、「カードの裏を通るループ」の見た目になる。

Phase 24 テスト仕様の MN-98（「間のノードカードをまたがないループ」）は本決定で「交差は背面通過を許容し全回避は保証しない」へ改定される。

### 3-3. 世界矩形・フィットとの関係

`worldBounds` は縦後退エッジの曲線極値（`cubicBounds`）を含める従来の仕組みを維持する。
張り出し量が必ず外縁＋余白の範囲に収まるため、世界矩形は最大でもノード矩形＋余白・帯幅程度に留まり、従来の「巨大化 → ノード矩形へのフィット退避」は構造上発生しなくなる。
`topologyKey` へのエッジ極値署名・フィット退避ロジック・CJ/CK の堅牢化には手を入れない。

### 3-4. 暫定解釈

- `off_s` の計算で `mids` の外縁が端点の内側にある構成（端点が既に全ノードの外側）は `off_s` が負または微小になり得るが、下限値で補うため常に正の張り出しになる
- 近似係数 K=0.75 は厳密ではないため、補正は `cubicBounds` 実測で確認して不足のみ足す方向に固定し、過剰側の再計算は行わない（外縁を超えてもよい。目標は最小到達であり上限ではない）
- 同量判定の 1px 未満は実装定数とする。厳密な同値でなくてもよく、左右差がこの幅内なら「ソースに近い外縁側」へ寄せる意図である

## 4. 受け入れ条件

- `recipe-heavyXiragen01` の計画（循環＋共有設備で全行をまたぐ後退エッジを含む）で、ループがノード群の外縁＋余白の範囲に収まり、画面外へ巨大にはみ出す弧が消える
- `芽針 → 採種機` は左側へ小さく膨らむループになる（左右同量でソースが左端のため）
- 全行スパンの `精錬炉 → 炭塊/赤銅塊` は外周を回る弧として描かれ、従来（採用側で張り出し 560〜920px・候補値は約 2,600px）より収まる
- ループがノードカードと交差する部分はカードの背面に隠れて見える
- 横表示・前進エッジ・単純循環（種↔作物）の描画は従来どおり
- `dotnet build`・`dotnet test` 全緑、`tools/validate_master.py` 通過（データ未変更の回帰確認）

## 5. 検証計画

- 自動テスト：変更は `flow-graph.js` の描画幾何のみで、xUnit の対象外。既存全緑を回帰確認する
- 手動確認：`docs/phases/test-specification-phase37.md` の MN-158〜 をブラウザ（WebGPU 対応 Chrome）で実施する
- 幾何の実測：CDP 経由の `__fg` 計装パターン（testing-blazor-apps-flow-graph スキル）で後退エッジの制御点・曲線極値を取り、外縁＋余白への到達と巨大化の解消を数値で確認する（計装は検証後に除去する）

## 6. リスクと引き継ぎ

- 交差許容は見た目の仕様変更を含む。実機で「カードの裏を通る弧」の見た目が自然に見えるかは MN-163 で確認する。見た目が悪い場合は複合経路化（本 Phase のやらないこと）の再検討が必要で、その際は別 Phase として起案する
- 張り出し量の近似係数・補正回数は実装定数であり、実測で外縁へ未達が残る配置があれば補正回数を増やすか係数を見直す
- 横表示の後退エッジにも同種の「回避不能なら巨大になる」問題は潜在するが、横表示には回避機構自体がなく世界矩形にも含めないため、本 Phase では顕在化しない。必要になれば別 Phase で扱う
