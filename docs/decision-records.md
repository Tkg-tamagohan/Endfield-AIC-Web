# 仕様決定記録（次期版）

次期 Web アプリ（[requirements.md](requirements.md)）のレビューと協議で確定した、仕様上の判断事項を記録する。
本記録は新規リポジトリでの作り直しに伴う新しい番号体系であり、旧リポジトリの決定は「旧 BA」のように参照する。
確定した決定は requirements.md 本文の該当箇所にも反映し、本文と本記録が矛盾しない状態を保つ。

| # | 項目 | 決定 |
|---|------|------|
| A | リポジトリ戦略 | 新規リポジトリ `Tkg-tamagohan/Endfield-AIC-Web` で作り直す。既存リポジトリ `Endfield-AIC-Planner` は参考実装として凍結し、README に凍結と後継への案内を追記する。GitHub Archive は新アプリ稼働後に判断する。本決定記録は新番号体系とし、旧リポジトリの仕様決定は「旧 BA」のように参照する |
| B | アーキテクチャ | Blazor WebAssembly（スタンドアロン、.NET 8）＋ Cloudflare Pages の静的配信のみで構成し、Workers・D1 は持たない。マスタ JSON はビルド成果物への静的同梱で配信する。共有データ（共有レイアウト・ユーザー紐付けデータ）が復活した時点でサーバー側要素の追加を再検討する |
| C | 移植範囲 | Core のモデル・計算・検証を C# のまま移植し、新モデルへ適合修正する（Core は外部依存ゼロの net8.0 で、WASM 上でそのまま実行できることを確認済み）。Infrastructure（EF Core・SQLite）・Layout・WPF（App/Admin）・旧 JSON との相互互換は移植しない。マスタ JSON スキーマは新系統で v1 に振り直す（旧データは実投入前の骨格のみで移行需要がないため） |
| D | マスタの正本と更新経路 | 正本は新リポジトリ内のマスタ JSON とし、PR レビュー＋CI/ローカル検証で管理する。Pages のデプロイで配信され、更新は JSON 差し替えコミットで行う。サーバー側の即時配信経路は持たない |
| E | 管理ツールの形と公開範囲 | 管理ツールは、ブラウザ内でマスタ JSON を読み込み・編集・検証・計算プレビュー・エクスポートする別 Blazor WASM アプリとする。別 Pages（専用ドメイン）にデプロイし、Cloudflare Access（Zero Trust 無料枠、メール OTP）で管理者以外を遮断する。公開アプリと同一 WASM 内のルート分離は、クライアント側ルーティングで回避できるため採らない。書き込み API は持たず、エクスポート物をリポジトリへコミットする運用とする |
| F | 既定のレシピ選択と将来の最適化 | 既定は `VersionAdded` 最新のレシピ × `CycleTime` 最小のペアとし、アイテム単位の代替選択（RecipeOverride 相当）でユーザーが切り替える。リリース後に「設備台数最小」「消費電力最小」「基礎素材最小」「設備面積最小」の最適化バリエーションを実装する予定とし、その前提として設備は縦横の大きさを保持する。設備面積最小の計算はパイプ・ベルトコンベアの経路を考慮しない |
| G | 設備の属性 | 計算ドメインの設備は共通属性（N）に加え、`Width`・`Height`・`PowerConsumption` を持つ。縦横は「設備面積最小」最適化（F）のために保持する。合成設備の保持枠・入出力ポートは廃止（W）。発電設備の識別属性は発電モデル廃止（Y）に伴い持たない |
| H | 環境モデル | `Environment` エンティティを新設し、消費アイテム（ItemId＋個/s）・供給設備（FacilityId）を持つ（供給範囲は廃止、W）。環境条件は RecipeFacility ペアの属性（`EnvironmentId`、null=不要）とする。イベント限定環境は現状存在しないが、`GameEventId` を同型で持てるようにする |
| I | 環境の計算反映 | 散布機のカバー範囲は、レイアウト機能を持たないため計算・保持ともに行わない。散布機の台数はユーザーが環境ごとに整数で指定でき、既定はその環境を必要とする稼働中レシピ数（レシピにつき 1 台）。環境の消費アイテム（ガス 6/s 等）×台数を需要へ追加し、散布機を設備要件・消費電力に計上する |
| J | 固定消費 | 設備が稼働するだけで消費される動力素材（アイテムの生産効率にかかわらず消費される継続消費）を、RecipeFacility ペアの要素（ItemId＋個/s、任意）として持つ。設備側の属性としないのは、レシピごとに値が変わりうる仕様変更への耐性のため。消費量は台数に比例させて計算へ組み込む |
| K | 対象デバイスと除外機能 | スマートフォン対応を要件に含め、レスポンシブ UI とする。工場レイアウト・キャンバス・共有レイアウト・自動配線・レイアウト由来のエンティティ（Layout/PlacedObject/CollisionClass）は新アプリに持ち込まず、将来も戻さない。PWA・ユーザーアカウント・サーバー保存・協調編集・収益化は対象外 |
| L | 進捗によるレシピ制限 | ゲームバージョン・進捗によるフィルタ UI は持たず、最高効率レシピが使えない場合はユーザーによる代替選択で対応する |
| M | 期間指定の計算 | 毎秒・毎分のレート表示に加え、日・時・分で指定した期間の個数換算を出力する。設備の消費電力合計は時間換算しない |
| N | 共通属性 | 全マスタエンティティ（Item・Environment・Recipe・Facility・GameEvent）に `Id`・`Name`・`Description`・`IconKey`・`VersionAdded`（＋`VersionRemoved`、任意）を持たせる |
| O | 流量調整の表示 | 計算結果は「未調整（切上台数の最大稼働）」と「調整済（推奨流量制限で余剰抑制）」の 2 状態を切り替えられるようにする。目標レートがレシピ出力の整数倍でない場合は既定を調整済とする |
| P | RecipeFacility のキー | ペアの一意性は全要素の組（RecipeId・FacilityId・CycleTime・EnvironmentId・固定消費）で判定する |
| Q | 発電 | v1 では発電モデルを実装しない（現行スコープに発電・工場系要素がないため）。消費電力合計のみを出力する。発電モデル自体は廃止（Y）とし、旧実装（仮想アイテム・定格発電・燃料ループ）は参考情報として残すに留める |
| R | 継承する既存決定 | 次の既存決定を継承する: 副産物の他素材要求への充当と余剰表示（旧 K）、循環依存の検出と警告、輸送容量警告（ベルト 30 個/s・パイプ 60 個/s、旧 L 一部）、需要アイテムへの既定選択規則とペア選択規則（旧 I/BC）、計画内のレシピ→設備一意と衝突時の先勝ち＋警告（旧 BN）、1 アイテムの需要を複数設備へ分割しない（旧 BE）、ペア基準の整合性ガード（旧 Z・旧 BP 相当の意味検証）、アイコン規約（IconKey・マニフェスト・権利クリア画像のみ、旧 AM/AO/AP）、`DataVersion`/`SchemaVersion` による版管理と全置換更新（旧 Q/P）、有効イベントのコンテキスト指定（旧 AG 相当）、複数目標（旧 D）、基礎素材の個/分表示（旧 C） |
| S | Origin | 廃止する。旧 `Origin`（Seed/User/Import）は Admin 作業 DB の行識別が用途であり、正本 JSON 単独管理の新モデルでは区別を持たない |
| T | イベント体系 | `GameEventId` を Item・Environment・Recipe に一様に持たせる（null=常設）。`GameEvent` は `Id`・`Name`・`ActiveFrom`・`ActiveTo`（null=期間なし・常設）。非有効イベントのイベント限定アイテムは生産・外部調達とも不可とし、需要が残れば未充足＋警告とする |
| U | 属性の異なるペア行の既定選択 | 同一 (RecipeId, FacilityId) で属性の異なるペア行が複数ある場合、既定は `CycleTime` 最小とし、同率は `EnvironmentId=null` を優先、さらに `FixedConsumption` なし/小を優先する。代替選択 UI はペア行単位で提示し、環境の有無が分かるよう併記する |
| V | 固定消費の台数基準 | 固定消費の需要計上は切上台数（実設置台数）×個/s とし、調整済モードでも同じ基準とする。稼働中に継続消費するモデルのため、必要台数の実数値ではなく実設置台数が一貫する。ゲーム仕様で稼働率比例の消費が確認された場合は実数基準への変更を再検討する |
| W | 工場系属性の廃止 | 計算ドメインで使用しないため、Facility の `InternalSlots`・`InputPorts`・`OutputPorts` と Environment の `CoverageRadius` を削除する（G・H の保持方針を変更。`Width`・`Height` は F の最適化で使用するため保持）。将来工場系要素を作成する場合は、計算ドメインとは別の工場ドメインを用意して再定義する |
| X | イベント終了後の限定アイテム | 非有効イベントのイベント限定アイテムは生産・外部調達とも不可とし、需要が残れば未充足＋警告とすることを確定する（T の暫定扱いを正式採用）。ゲーム仕様で異なる挙動が確認された場合に再検討する |
| Y | 発電モデルの扱い | 廃止する。計算ドメインで使用しないため（Q の「将来の追加対象として温存」を変更）。将来再導入する場合は工場ドメインを別途用意して再定義する。消費電力合計のみを出力する方針は変わらない |
| Z | イベント期間の時刻解釈 | `GameEvent` の `ActiveFrom`・`ActiveTo` は時刻の瞬間（RFC 3339 の `Z`・オフセット付き表記）として解釈する。既定の有効判定は両端を閲覧者のローカル時刻へ換算した暦日で行い、`Z` とオフセット付きの書き方の違いで解釈が分かれないよう揃える。日付の読み取りは既定判定のたびに行い、ページを開き続けた場合も既定の鮮度を保つ（ユーザーが操作したチェックは既定の再評価から除外する） |
| AA | アイコンの正規化とアニメーション | アイコン画像の出力は 128×128 に揃える。クロップ領域が 128 ピクセルを超える画像は 128×128 へ縮小し、以下の画像は拡大せず原寸を透過キャンバスの中央に配置する。アニメーション画像（GIF・APNG 入力）は全フレームへ同一規則を適用し APNG で保存する。APNG は PNG の拡張形式のため、`icons/<Key>.png` のファイル規約・`image/png` の MIME・マニフェスト構造は変更しない。デコードは WebCodecs の `ImageDecoder` を主経路とし、APNG 入力は同梱する UPNG.js のデコード機能を副経路とする。いずれの経路も使えない場合に限り、先頭フレームの静止画へ縮退する |
